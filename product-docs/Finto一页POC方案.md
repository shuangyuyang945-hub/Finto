# Finto 一页验证方案

> 验证主题：专业项目交付中的验收要求与版本变更追踪
> 验证方式：1 个已完成的去标识化历史子案例 + 本人后续持续使用
> 产品阶段：单机本地个人实践工具，不作为多用户或生产系统承诺

## 1. 问题与核心假设

Finto 源于专业项目中的真实交付问题：验收要求散落在任务书、报告和反馈中；日期、范围和验收口径会变化；新反馈难以映射到具体交付物；直接修改会覆盖旧版本，并丢失“依据—决定—版本”的证据链。

本轮只验证一个最小假设：

> 当正式版本中的业务事实有误时，Finto 能否让本人根据合法、去标识化的依据提出变更，由负责人决定后创建新 Revision，同时保留旧版本、字段差异和审计记录？

历史案例回放是回顾性产品验证，不是外部用户试点，也不能证明市场需求、多人易用性或生产效果。

## 2. 已完成的简化子案例

| 项目 | 实际记录 |
|---|---|
| 业务问题 | 原第1版把后续市级成果报送节点误写为县级成果评审日期 |
| 纠错依据 | Source #10：两个报送节点、附件定位和事实边界 |
| 人工决定 | 删除错误的评审表述，只保留县级成果资料报送范围，并补充验收标准 |
| 影响类型 | 范围变化、验收变化 |
| 变更请求 | #1，先保存为待负责人决定，接受后才创建新 Revision |
| 验收清单 | 3 条，全部保持待验证，没有提前宣称交付通过 |
| 旧版本 | 第1版 Revision #5，继续保留并可查看 |
| 当前版本 | 第2版 Revision #6，经再次确认后成为当前版本 |
| 路径耗时 | 26 分 06 秒，从提出变更到确认第2版 |
| 隐私边界 | 不保存原文件路径、联系人、联系方式和详细地址 |

## 3. 本轮指标与结论

| 指标 | 实际结果 | 可以说明什么 |
|---|---:|---|
| 纠正的业务事实 | 1 处 | 系统支持把有依据的纠错转成受控变更 |
| 保留的 Revision | 2 版 | 新版没有覆盖旧版 |
| 待验证验收项 | 3 条 | 有要求依据不等于已经交付通过 |
| 人工决定前新 Revision | 0 个 | 变更未绕过负责人 |
| 版本变更路径耗时 | 26 分 06 秒 | 只说明本次实际过程，不等于节省时间 |
| 要求覆盖率 | 未测 | 未验证全部 12 条要求 |
| 人工基线耗时 | 未测 | 不能计算效率提升 |
| 外部用户与多人验证 | 未测 | 不能外推市场价值或协作能力 |

本轮不能使用“准确率”“节省比例”或“全部覆盖”等表述。

## 4. 已验证路径

```text
只读核对已授权原资料
→ 生成去标识化字段依据 Source #10
→ 定位第1版中的错误业务事实
→ 提出范围与验收变更
→ 保存为待负责人决定
→ 负责人核对字段差异、影响和验收项
→ 接受后创建第2版 draft
→ 验收负责人再次确认
→ 第2版成为当前版本，第1版继续保留
→ 查看完整变更报告与审计事件
```

## 5. 后续复用规则

后续只在自然出现、合法且已去标识化的真实变更场景中追加记录，不为了凑案例数量强行制造任务。每次至少记录：

- 原始问题与去标识化说明；
- 采用的来源、定位和事实边界；
- 修改前后字段；
- 影响类型和验收清单；
- 人工决定及原因；
- 新旧 Revision 是否完整保留；
- 实际耗时；
- 本案不能证明什么。

## 6. 已实现范围

- 验收参考资料分类管理；
- PDF、DOCX、XLSX、CSV、TXT、Markdown 文件导入及原件保留；
- 任务级来源授权、字段级证据和待确认项；
- 变更影响分析与人工决定；
- 接受后创建新 Revision，不覆盖旧 Revision；
- 历史版本筛选、详情和可打印变更报告；
- 失败候选审计与正式表零污染。

## 7. 明确暂缓

- 为了完成计划强行补做第2、第3个历史案例；
- 干净 Windows 环境安装验收；
- 多人账号、登录身份和并发协作；
- 全量向量 RAG 和自动读取所有资料；
- 多 Agent 编排；
- 外部消息通知；
- 泛化项目管理、排期和资源管理；
- 用本人案例回放冒充外部用户验证。

## 8. 当前结论

> Finto 已在 1 个去标识化历史子案例中完成有依据的版本纠错：纠正 1 处业务事实，经人工决定创建并确认第2版，同时保留第1版、字段差异、3条待验证验收项和变更审计。该结果证明单机单用户场景中的版本纠错与追溯能力；由于没有人工基线耗时、全部要求覆盖或外部用户验证，不能声称效率提升、完整覆盖、市场需求或生产可用性。
