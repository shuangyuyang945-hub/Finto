# Finto 简历项目与面试表达

> 使用原则：只表达已经发生并有证据的事实。Finto 当前是单机本地 POC，不写“生产落地”“企业级平台”或未经验证的效率提升比例。

## 一、简历项目经历

### 项目名称

**Finto｜可追溯的 AI 项目交付工具**

### 推荐主版本：AI 应用解决方案 / AI 应用交付

针对项目要求、截止日期和验收标准分散且持续变化的问题，设计并交付单机本地 AI 应用 POC。主导业务问题定义、Project/Cycle、Deliverable/Revision、AgentJob 和 Source 对象建模，设计“授权资料—结构化候选—人工决定—版本变更—历史追溯”闭环；在 AI 辅助下完成 Python、SQLite 和原生 JavaScript 实现。系统支持零 Token 确定性解析与 OpenAI-compatible 模型调用，并通过自动化回归保护来源越权、资料失效、Prompt Injection、重复提交、跨项目操作和人审前零写入等边界。基于一次真实用户试用关闭“创建草稿后不知道下一步”等问题；又用一个去标识化历史子案例纠正 1 处业务事实，保留旧版并形成当前确认的新 Revision。GitHub Actions 已发布 Windows `v0.5.0` 安装包，但当前本地新增能力不冒充已进入该发布版。

### 三条精简要点版

- 将“要求分散、标准变化、旧版本易被覆盖”的交付问题建模为 Project/Cycle、Deliverable/Revision、AgentJob 和人工审查闭环，明确 AI 只生成候选，正式事实由负责人决定；
- 设计任务级来源授权和字段级证据链，支持零 Token 与模型两种路径；未授权、停用、删除或无证据来源被拒绝，失败候选保留审计且正式表零写入；
- 在 AI 辅助下完成 Python + SQLite + 原生 JavaScript POC、关键风险自动化回归、一次真实用户试用改进和一次去标识化版本纠错回放，并通过 GitHub Actions 发布 Windows `v0.5.0` 安装包。

## 二、不同岗位的适配段落

这些版本使用同一组事实，只调整叙事重点，不能同时写成四个独立项目。

### AI 产品运营版

从真实用户“要求分散、验收标准变化、创建草稿后不知道下一步”的问题出发，定义 Finto 的项目交付主路径和人机责任边界；组织一次真实用户试用，将术语理解、入口顺序和下一动作问题转成可验证需求，推动待审说明、写入预览和草稿确认入口改进。随后用去标识化历史资料回放一次版本纠错，核对依据、影响和人工决定，确认新旧 Revision 可以追溯。用停止条件和 Professional Pushback 控制功能扩张，避免把自动化等同于自动决策。

### 国内实习级 FDE 版

完成从模糊业务问题到可运行交付结果的 Echo + Delta 闭环：把分散要求和版本争议转成对象、状态、权限和验收合同，并在 AI 辅助下落地为 Python/SQLite/JavaScript POC；用去标识化资料、来源授权、人审和失败审计控制现场风险，形成 README、SOP、POC、演示脚本和 Windows Release，可向使用者说明能力边界与下一阶段条件。

### AI 项目运营版

围绕 Project/Cycle、交付物版本和责任状态建立可追溯台账，把授权资料、AI候选、人工决定、正式 Revision、测试与验收连接起来；用 400/403/404/409 等失败分类、审计记录和零污染检查管理风险，通过真实用户反馈关闭最高价值问题，并形成版本发布、故障处理和交接材料。

## 三、面试题 1：你为什么做 Finto？

### 60 秒回答

> 我最开始看到的问题不是“缺一个聊天机器人”，而是项目要求、截止日期和验收标准散落在不同资料里，而且会发生变化。负责人要反复确认当前以哪份为准，执行者可能按照旧要求返工。直接让 AI 修改正式内容又会出现来源越权、猜测缺失信息和覆盖历史的问题。
>
> 所以我把范围收敛成一个最小闭环：负责人选择本次允许使用的资料，系统生成带字段级依据的候选，负责人接受、修改或拒绝，只有人工确认后才创建新的草稿版本。这个设计既利用 AI 做整理，又不让 AI 替代业务责任。

### 面试官真正想听什么

- 你是从业务问题出发，不是先有模型再找场景；
- 你能主动缩小范围；
- 你知道效率和责任边界需要同时设计。

### 不要这样说

> 我想做一个 AI 项目，所以做了一个能自动生成交付物的平台。

问题：没有真实场景，也错误暗示 AI 能直接生成正式交付物。

## 四、面试题 2：这个系统的核心流程和对象是什么？

### 90 秒回答

> Project 表示这次业务交付属于哪个项目，Cycle 表示当前是哪一轮工作。Deliverable 表示最终要交付什么，Revision 保存每一版内容和状态，所以新要求出现时不会覆盖旧版本。
>
> AI部分使用 AgentJob。创建任务时会冻结 action、instruction、允许使用的 source IDs、禁止范围和请求合同。运行后生成结构化候选、实际使用来源、字段级 evidence、locator 和待补充与确认信息。系统先校验结果有没有越过授权、来源是否仍然可用、字段是否有证据，然后候选进入人工审查。
>
> 项目负责人可以原样接受、修改后接受或拒绝。接受后才创建 draft Revision；之后由验收负责人确认，再进入制作、提交和验收状态。这样来源、任务、候选、人工决定和正式版本可以完整追溯。

### 一句话结构

> 项目和周期确定范围，交付物和版本保留历史，AgentJob 控制 AI 权限，人工审查决定什么能成为正式事实。

## 五、面试题 3：你如何保证 AI 结果可靠，不污染正式数据？

### 90 秒回答

> 我没有把“JSON格式正确”当成业务正确，而是分三层校验。
>
> 第一层是来源权限：结果中的 used sources、字段级 evidence sources 和 unknowns 中记录的已检查来源，都必须属于任务创建时冻结的授权集合，而且来源在结果提交时仍需可用。未授权、停用或删除来源会返回 403。
>
> 第二层是内容证据：即使 Schema 合法，如果候选字段没有可验证的来源定位和原文，结果仍然被拒绝；资料没写清楚的内容进入待补充与确认，不能由模型猜测。Prompt Injection 也不能改变已经冻结的任务合同。
>
> 第三层是数据库边界：候选失败、重复运行、跨项目操作或人工审查前，Deliverable 和 Revision 必须零写入；失败现场和拒绝原因保留在审计表。我用自动化回归保护这些规则，但不把测试数量等同于模型准确率或真实业务效果。

### 追问：“为什么返回 403，不是 400？”

> 400 表示请求格式或必填字段错误；来源未授权或不可用时，请求结构可能完全合法，但没有使用该来源的权限，因此用 403。对象不存在用 404，业务状态冲突用 409。

## 六、面试题 4：这个项目里哪些是你做的，AI 做了什么？

### 90 秒回答

> 我的主要贡献是业务判断和验收，不是把 AI 生成的代码全部算成独立编码。我定义了真实问题和第一版不做范围，逐步确定 Project、Deliverable、Revision、AgentJob 和 Source 的关系；对状态码、权限、人工责任、来源失效、失败审计和正式表零写入作出判断；运行并解读关键测试，参与真实用户试用，把用户卡点转成需求和验收标准，并负责最终页面和业务闭环验收。
>
> AI主要帮助我补齐测试脚手架、实现 Python/SQLite/JavaScript 代码、整理文档、定位错误和执行回归。我没有直接接受所有生成结果，而是通过失败测试、数据库查询、页面操作和 Git diff 检查它是否符合业务合同。GitHub 发布、仓库清理和 Release 产物也经过实际验证。
>
> 如果要准确概括，我负责定义“什么问题值得解决、什么不能做、怎样算完成”，AI帮助提高实现和验证速度。

### 这一题的核心

> 不隐瞒 AI，也不把自己降格为只会提需求。你的价值是判断、边界、验收和推进闭环。

## 七、面试题 5：当前最大的限制是什么？下一步怎么做？

### 90 秒回答

> 当前版本适合单机本地受控 POC，还不是多人生产系统。主要限制有四个：负责人字段只是业务记录，不是登录身份鉴权；远程部署、并发、配额和运行监控没有完成；干净 Windows 环境安装验收已经暂缓；业务验证只完成了一个去标识化简化子案例，没有覆盖全部 12 条要求，也没有记录人工基线耗时。
>
> 下一步我不会为了凑数量强行增加案例或扩建大平台。我会先把已经发生的真实纠错持续记录清楚，在后续自然出现的去标识化变更场景中继续验证来源、人工决定、版本保留和耗时。如果多次使用仍能稳定解决问题，再评估身份权限、来源版本冻结和运行监控；如果价值不稳定，就停止扩张并保留失败原因。
>
> 如果后续证据支持继续投入，工程优先级是登录身份与角色权限、来源内容版本冻结和运行监控，而不是先上多 Agent 或全量 RAG。

### 追问：“为什么不先做 RAG？”

> 当前最关键的问题不是召回更多资料，而是明确本次允许使用哪些资料、字段依据是什么、谁决定写入以及如何保留版本。授权和责任闭环没有完成时，扩大召回范围只会扩大风险。

## 八、面试题 6：讲一次真实业务验证

### 60 秒回答

> 我用本人参与过的一份去标识化历史资料回放 Finto，发现正式第1版把后续市级成果报送节点误写成了县级成果评审日期。我没有直接修改数据库，而是只读核对原通知附件表格，把县级和市级报送时间整理为 Source #10，再通过页面提出范围与验收变更。
>
> 负责人核对修改前后字段、影响类型和三条验收项后接受变更，系统创建第2版草稿；再次确认后，第2版成为当前版本，第1版仍然可以打开。变更请求、决定原因、字段差异和来源均保留。从提出变更到确认第2版实际用了26分06秒。
>
> 这个结果证明了单机单用户场景中的版本纠错和追溯能力，但因为没有记录人工基线耗时，也没有验证全部12条要求，所以我不会把它说成效率提升、完整覆盖或多人生产验证。

### 这段经历证明什么

- 能从原始依据中区分两个容易混淆的业务节点；
- 能把错误转成变更影响、验收项和人工决定；
- 能同时给出真实结果和不能外推的边界。

## 九、30 秒项目总结

> 我做的 Finto 是一个可追溯的 AI 项目交付 POC。它把授权资料、候选、人工决定和 Revision 历史连成一条证据链，AI 或本地规则只能生成候选，负责人决定什么能成为正式版本。我完成了零 Token 与模型路径、关键风险回归、一次真实用户改进和 Windows `v0.5.0` 发布；还用一个去标识化历史子案例纠正了1处业务事实，并保留新旧两个版本。当前结果证明版本纠错和追溯能力，但不能证明效率提升、全部要求覆盖或多人生产价值。

- [ ] 能讲清 Source #10、变更请求 #1、第1版和第2版之间的关系；
