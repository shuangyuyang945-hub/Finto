# Finto 项目复习指南

> 复习范围：Day1—15 的业务建模、受控 AI、人工审查、版本追溯与项目交付成果。
>
> 目标：能独立讲清业务问题、系统边界、完整流程、真实证据和仍未验证的部分。

## 一、先记住这一句话

> Finto 把负责人本次授权的项目资料整理成带字段级依据的候选，经过系统校验和人工审查后，才创建新的正式草稿版本。

这句话包含 Finto 的五个核心设计：

1. **有业务范围**：候选属于一个明确的 Project 和当前 Cycle；
2. **有权限范围**：AgentJob 只可使用创建时冻结的来源；
3. **有证据**：候选字段能够回到来源、定位和原文摘录；
4. **有人负责**：AI 生成候选，负责人接受、修改或拒绝；
5. **有版本历史**：变化形成新 Revision，不覆盖旧 Revision。

Finto 不是聊天机器人、全自动项目经理或已经上线的企业平台。当前准确定位是：

> 一个具备本地受控 POC 条件的可追溯项目交付工具。

## 二、Finto 为什么存在

### 1. 真实业务问题

项目要求、截止日期和验收标准可能分散在任务书、反馈和讨论记录中，而且会发生变化。负责人难以及时确认当前有效内容，执行者也可能按照旧要求工作，最终造成遗漏和返工。

### 2. 为什么不能让 AI 直接修改正式内容

如果 AI 自动写入正式交付物，会出现四类责任风险：

- 使用了本次没有授权的资料；
- 把资料中没写清楚的内容猜成事实；
- 直接覆盖旧版本，事后无法还原变化过程；
- 负责人没有检查新旧内容，无法判断谁对正式结果负责。

### 3. Finto 的最小解法

```text
负责人选择本次资料
→ 系统冻结任务合同
→ 零 Token 规则或模型生成候选
→ 系统校验来源、证据和结构
→ 负责人接受、修改或拒绝
→ 创建新的 draft Revision
→ 后续确认、执行、提交与验收
```

核心判断不是“要不要 AI”，而是：

> AI 可以提高整理速度，但不能绕过授权、证据、版本和人工责任。

## 三、核心业务对象地图

| 对象 | 通俗解释 | 主要责任 |
|---|---|---|
| Project | 这次业务交付属于哪个项目 | 限定业务范围；非 active 时禁止创建正式业务对象 |
| Cycle | 当前处于哪一轮工作 | 区分同一项目的不同工作周期 |
| Source | 可被阅读的项目资料 | 保存资料内容、可用状态和 `ai_access` |
| AgentJob | AI 或本地解析本次收到的任务合同 | 冻结 action、instruction、授权来源、禁止范围和请求合同 |
| Candidate Result | 系统整理出的候选答案 | 保存结构化候选、实际使用来源、证据和待确认信息 |
| Deliverable | 最终要交付什么 | 作为交付成果的稳定身份，指向当前 Revision |
| Revision | 这个成果当前是哪一版、以前是什么样 | 保存每一版内容和状态，避免覆盖历史 |
| Audit | 谁在什么时候做了什么决定 | 保存成功、失败、拒绝和状态流转证据 |

一句话串联：

> Project/Cycle 确定范围，Source 提供资料，AgentJob 控制权限，Candidate Result 承载候选，人工审查决定是否形成 Deliverable/Revision，Audit 记录全过程。

## 四、一次完整业务闭环

### 第一步：建立业务范围

创建或选择 active Project，并明确当前 Cycle。项目不处于 active 状态时，不能写入 Deliverable 和 Revision。

### 第二步：准备并授权资料

负责人添加资料，再逐次选择本任务允许使用的 Source。`ai_access=1` 表示该来源允许进入任务；`ai_access=0`、已停用或已删除的来源不可用。

授权不是“系统可以读取资料库全部内容”，而是“这一次任务可以读取哪些资料”。

### 第三步：冻结 AgentJob

任务创建时冻结：

- `action`：本次要执行什么动作；
- `instruction`：本次具体要求；
- `allowed_source_ids`：允许使用哪些来源；
- `forbidden_scope`：明确禁止哪些行为；
- request/schema：输入和输出合同。

资料正文中的 Prompt Injection 不能改变这些冻结内容。

### 第四步：运行并生成候选

Finto 有两种显式运行方式：

| 模式 | 适合情况 | 边界 |
|---|---|---|
| 零 Token 本地解析 | 资料有“阶段成果、交付时间、验收要求”等明确字段 | 不调用模型，只提取明确内容，不猜测 |
| AI 模式 | 表达分散、需要语义理解 | 调用负责人配置的 OpenAI-compatible 服务，可能产生费用 |

系统不会擅自从零 Token 切换到 AI 模式。无论使用哪种模式，结果都先进入人工审查。

### 第五步：校验候选

系统检查：

- `used_source_ids`：结果实际使用了哪些资料；
- 字段级 `evidence_source_ids`：每个字段由哪些资料支持；
- 来源 locator 与 evidence excerpt：证据位于哪里、原文是什么；
- 待补充与确认信息中的 `checked_source_ids`：系统检查过哪些资料仍无法确定；
- 上述来源是否都属于冻结授权，并且提交结果时仍然可用；
- 结果是否符合结构和字段合同。

“JSON 格式合法”不等于“业务请求合法”。如果实际来源减去授权来源后的差集非空，候选必须被拒绝。

### 第六步：人工决定

负责人可以：

- 原样接受；
- 修改名称、期限、验收标准、负责人等字段后接受；
- 合并多个候选并修改后接受；
- 拒绝候选。

页面中的写入预览必须根据真实修改动态生成，不能只覆盖少数预设组合。交付依据可以由负责人选择添加或不添加。

### 第七步：形成正式版本

只有人工接受或修改后接受，系统才创建正式的 draft Revision。之后按照：

```text
draft → confirmed → doing → submitted → accepted
```

进行流转。状态属于 Revision；Deliverable 的 `current_revision_id` 指向当前版本。

业务范围、期限或验收标准变化时，应创建新 Revision。旧 Revision 保留旧内容、旧状态和旧审计，不直接覆盖。

## 五、失败时为什么仍然可信

### 状态码速记

| HTTP | 业务含义 | 例子 |
|---|---|---|
| 400 | 请求格式或必填字段错误 | 缺少必填字段 |
| 403 | 没有权限，或引用了未授权/不可用来源 | 结果引用 Source 99，或 `ai_access=0` |
| 404 | 对象或接口不存在 | Project、AgentJob 不存在 |
| 409 | 请求与当前业务状态冲突 | 非 active Project 创建 Deliverable |
| 422 | 模型输出能解析，但不符合结果合同 | 字段结构或证据合同不合格 |
| 502 | 外部 AI 服务调用失败 | API 地址、密钥、模型或服务异常 |
| 500 | 未预期程序异常 | 使用 `request_id` 对应脱敏错误日志 |

### 失败写入边界

候选被拒绝时允许保留：

- failed AgentJob 及原授权快照；
- rejected Candidate Result；
- 实际引用的 source、locator 和 excerpt；
- 拒绝数量、原因和失败审计。

但必须保证：

- Deliverable 零变化；
- Revision 零变化；
- 成功审计为 0；
- 失败审计可追溯。

这就是 Finto 的“失败不会污染正式业务事实”。

## 六、Day14：把代码变成可交付成果

Day14 的重点不是增加功能，而是让现有产品具备被别人理解、启动、验证、排障和试点的基本条件。

| 成果 | 解决的问题 | 复习时要会说什么 |
|---|---|---|
| README 与产品蓝图 | 别人不知道产品是什么、如何启动 | 一句话定位、完整业务链、当前能力与限制 |
| Health 接口 | 不知道应用是否正常启动 | 先检查 `/api/health`，再区分业务拒绝和程序异常 |
| 脱敏错误日志与 SOP | 500 难定位，排障可能泄露资料 | 用 `request_id` 查日志；不记录正文、密钥或异常原文 |
| 一页验证方案 | 个人实践无法形成可信业务证据 | 用去标识化历史资料验证来源、变更和版本追溯，不预设必须完成多个案例 |
| Professional Pushback | 客户提出高风险自动化时只会说“不” | 先承接目标，再说明风险，给更小替代方案，锁定下一决定 |
| 自动化测试 | 业务规则修改后容易回归 | 产品回归测试保护权限、证据、人审和零污染等规则 |
| Windows Release | 代码没有可交付载体 | GitHub Actions 已生成 `v0.5.0` 安装包和发布产物 |
| 仓库清理 | 学习过程和产品成果混在一起 | 公开仓库只保留成熟产品实现、测试、配置和交付文档 |

### 已验证与尚未验证

| 已验证 | 尚待验证 |
|---|---|
| 本地业务主链可运行 | 在另一台或干净 Windows 电脑上的真实安装验收 |
| 一个去标识化历史子案例完成版本纠错闭环 | 人工整理基线耗时与可比较的效率提升 |
| Source #10、变更请求 #1、Revision #5/#6 可相互追溯 | 全部业务要求的覆盖情况 |
| 修正前后两个版本均保留，3 个验收项继续处于待验证状态 | 更多独立案例和长期持续使用表现 |
| 产品自动化回归测试通过 | 多人身份、权限、并发和远程部署 |
| GitHub Actions 成功生成 `v0.5.0` 产物 | 干净 Windows 环境的真实安装验收 |
| 授权、失败审计和正式表零污染边界有测试保护 | 长期运行成本、时延、稳定性和生产监控 |
| 有一次早期可用性观察及对应改进 | 多用户价值尚未验证，也不作为当前阶段的完成条件 |

注意：构建成功不等于干净电脑安装成功；自动化测试通过也不等于模型准确率、业务价值或生产可用性。

## 七、Day15：把成果讲清楚

Day15 的三种表达使用同一组事实，但回答的是不同问题。

| 场景 | 对方最关心什么 | 表达重点 |
|---|---|---|
| 3 分钟产品 Demo | 它到底怎么工作 | 授权、候选、证据、人审、Revision 闭环 |
| 7 分钟方案 Demo | 是否值得继续验证 | 业务问题、风险、回放指标、停止条件和下一决定 |
| 简历与面试 | 你在项目中做了什么 | 业务判断、对象和边界设计、验收、AI 协作与诚实限制 |

### 3 分钟产品 Demo 记忆骨架

1. **0:00—0:30**：要求分散且变化；直接自动写入有风险；
2. **0:30—1:10**：选择资料、运行方式和指令，冻结任务边界；
3. **1:10—2:05**：检查候选字段、来源依据和待补充与确认信息；
4. **2:05—2:40**：负责人原样接受或修改后接受，创建 draft Revision；
5. **2:40—3:00**：展示交付清单和历史版本，说明当前限制。

收尾句：

> Finto 不替人做正式决定，而是让系统完成有边界的整理，让负责人依据证据决定什么成为正式版本。

### 7 分钟方案 Demo 记忆骨架

1. 先讲客户问题，不先讲模型；
2. 解释为什么不能让 AI 直接改正式字段；
3. 用一条业务链说明授权、候选、人审和版本；
4. 演示最小闭环；
5. 说明可靠性和失败边界；
6. 展示一个真实的去标识化版本纠错案例，而不是冒充外部试点；
7. 主动说明限制，并用真实记录决定下一步。

### 已完成的历史案例验证

本轮使用一份去标识化历史资料完成了版本纠错：

- 授权依据：Source #10；
- 变更对象：Deliverable #3；
- 处理记录：变更请求 #1；
- 历史版本：Revision #5 保留原内容，Revision #6 成为当前确认版本；
- 验收状态：3 个验收项仍为待验证，没有把尚未验收的内容写成已完成；
- 操作耗时：从提出变更到确认新版本共 26 分 06 秒。

这次验证证明了版本纠错、证据保留和历史追溯能力；没有人工整理基线，因此不能据此声称效率提升，也不能据此证明全部要求已覆盖。后续只有在出现新的关键疑问时才增加案例，不再为了凑数量重复验证。

## 八、面试时如何说明自己的贡献

### 你负责的部分

- 定义真实问题和第一版不做的范围；
- 确定 Project、Cycle、Deliverable、Revision、AgentJob 和 Source 的关系；
- 判断权限、证据、版本、人工责任和状态码；
- 把风险写成测试预期，运行测试并理解失败原因；
- 参与一次早期可用性观察，把界面卡点转成需求和验收标准；该记录不用于证明多人业务价值；
- 对页面、数据库边界、发布结果和最终闭环作验收判断。

### AI 辅助的部分

- 补齐测试脚手架和实现代码；
- 协助定位错误、整理文档和执行回归；
- 帮助实现 Python、SQLite 和原生 JavaScript POC；
- 协助生成构建和发布配置。

准确的总结是：

> 我负责定义什么问题值得解决、什么不能做以及怎样算完成；AI 帮助提高实现和验证速度。我通过测试、数据库检查、页面操作和代码差异验收结果，而不是直接接受 AI 输出。

### 五个高频面试问题

1. **为什么做 Finto？**

   要求分散且变化；直接自动写入会带来越权、猜测、覆盖历史和责任不清。

2. **核心流程和对象是什么？**

   Project/Cycle 管范围，Deliverable/Revision 管版本，AgentJob 管 AI 权限，人工审查决定正式事实。

3. **怎样防止 AI 污染正式数据？**

   授权校验、字段级证据、待确认信息、人审前零写入、失败审计和新 Revision。

4. **你做了什么，AI 做了什么？**

   你负责业务判断、边界、验收和推进；AI 辅助实现、排错、测试和文档。

5. **当前最大限制和下一步是什么？**

   当前是单机本地受控的个人实践工具；已经完成一次真实版本纠错验证，下一步是持续自用并保留新的真实证据，不能提前声称效率提升、全部要求覆盖或多人价值。

## 九、专业 Pushback 怎么说

当客户要求“让 AI 把所有延期项目自动延后 7 天”时，不要只回答做不到。

使用四步：

1. **承接目标**：理解客户想减少人工逐项处理；
2. **明确风险**：不同交付物的阻塞、依赖和责任不同，统一延期可能产生错误正式事实；
3. **给出替代方案**：先用确定性代码筛选延期候选，再由负责人逐项决定；
4. **锁定下一决定**：确认试点范围、负责人、授权来源和通过条件。

这体现的不是保守，而是能够把客户目标变成可控、可验收的最小方案。

## 十一、当前限制与下一步优先级

当前限制：

1. 单机本地运行，没有多人登录身份、并发权限和远程部署；
2. 负责人目前是业务字段，不是已登录用户的真实身份鉴权；
3. 资料与项目的强关联、来源内容版本冻结仍需完善；
4. 外部 AI 服务的费用、可用性和质量由配置的服务决定；
5. 干净 Windows 环境安装验收已经暂缓，不能声称完成；
6. 已完成一个历史子案例，但没有人工基线，尚不能证明效率提升或全部要求覆盖。

建议顺序：

```text
保留本次版本纠错验证证据
→ 本人持续自用并记录新的真实问题
→ 只有新问题暴露时才做最小修正和补充验证
→ 只有出现真实外部需求，再评估身份、协作与部署
→ 继续暂缓全量RAG、多Agent和泛化项目管理
```

当前不再把补做 SQL、凑足三个案例或干净 Windows 安装作为本轮门槛；这些事项只有在新的求职或交付证据需要时再重新打开。

## 十二、主动回忆卡片

复习时先遮住答案，用自己的话回答。

1. **Finto 解决的不是哪类问题？**

   不是“缺少聊天机器人”，而是项目要求分散、变化且正式决策难追溯。

2. **为什么候选不能直接成为正式内容？**

   因为授权、证据、版本和业务责任必须由系统校验并由负责人确认。

3. **Project/Cycle 与 Deliverable/Revision 有什么区别？**

   前者确定业务范围和轮次，后者表示交付成果及其历史版本。

4. **AgentJob 冻结什么？**

   action、instruction、allowed source IDs、forbidden scope 和请求/结果合同。

5. **三组来源 ID 为什么都要检查？**

   used、字段 evidence、待确认信息 checked sources 分别可能暴露实际使用、字段依据和检查范围的越权。

6. **`ai_access=0` 是什么意思？**

   来源当前不可被 Agent 使用，即使任务或结果格式正确也必须拒绝。

7. **403 和 409 的区别是什么？**

   403 是无权使用来源；409 是操作与当前业务状态冲突。

8. **零 Token 是否等于没有 AI Native 设计？**

   不是。AI Native 的关键是工作流、边界和人机责任；明确字段可以优先走更便宜、更稳定的确定性路径。

9. **candidate rejected 与 Revision accepted 是一回事吗？**

   不是。前者是候选校验或审查结果，后者是正式版本状态。

10. **为什么不直接修改旧 Revision？**

    会丢失当时的内容、状态和验收依据，无法追溯变化。

11. **自动化测试证明什么？**

    证明已覆盖的一组工程规则当前通过，不证明模型准确率或生产可用性。

12. **Day14 最重要的变化是什么？**

    从“代码能跑”变成有启动、验证、排障、试点、发布和交接证据的产品成果。

13. **Day15 最重要的变化是什么？**

    能针对产品演示、售前决策和面试追问，用同一组真实事实进行不同表达。

14. **你的核心贡献是什么？**

    业务判断、对象和边界设计、验收标准、用户反馈转化和闭环推进。

15. **下一步为什么不是先做全量 RAG？**

    当前已经证明版本纠错和追溯闭环可运行，尚缺的是持续使用、效率基线和覆盖证据；扩大召回只会先扩大范围和风险。

## 十三、三轮复习法

### 第一轮：10 分钟建立全貌

只复述四句话：

1. Finto 解决什么问题；
2. 完整业务链是什么；
3. AI 为什么不能直接写正式表；
4. 当前已经验证和尚未验证什么。

### 第二轮：20 分钟走一次产品

在本地完成：

```text
选择项目
→ 添加资料
→ 授权并运行零Token任务
→ 检查候选、证据和待确认信息
→ 修改后接受
→ 创建draft Revision
→ 查看交付清单和历史版本
```

每一步都回答：“谁有权做？读取了什么？写入了什么？失败后保留什么？”

### 第三轮：30 分钟练表达

- 不看稿讲一次 30 秒项目总结；
- 按页面完成一次 3 分钟产品 Demo；
- 按客户决策逻辑完成一次 7 分钟售前 Demo；
- 回答五个高频面试问题；
- 从主动回忆卡片随机抽 5 题作答。

### 熟练完成标准

当你能够做到以下五点，就算已经熟悉 Finto：

- 不看文档，用 30 秒说清产品；
- 画出八个核心对象及关系；
- 独立走通授权、候选、人审、新 Revision 闭环；
- 用 Source #10、变更请求 #1 和 Revision #5/#6 讲清一次真实纠错；
- 解释一个 403 失败为什么没有污染正式表；
- 诚实说清已验证证据、当前限制和不应提前承诺的结果。
