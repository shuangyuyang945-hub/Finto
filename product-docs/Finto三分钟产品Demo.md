# Finto 三分钟产品 Demo

> 演示目标：用一个已经完成的去标识化历史子案例，展示 Finto 如何发现业务事实错误、让负责人决定变更、创建新版本并保留完整追溯链。
>
> 演示方式：只读展示现有结果，不现场调用模型、不新建业务数据，因此不依赖网络、API Key 或模型稳定性。

## 演示前准备

- Finto 已启动并打开“项目总览”；
- 当前选择“课程项目交付 · 第1周期”；
- 资料库中保留 Source #10“案例A附件报送节点去标识化摘录”；
- 交付清单中保留案例 A 交付成果的第1版和第2版；
- 变更请求 #1 的完整报告可以打开；
- 页面和讲解中不展示原文件路径、联系人、联系方式或详细地址。

## 0:00—0:30｜先讲真实问题

### 讲解

> Finto 当前最有价值的不是从资料里摘几个字段，而是当验收要求或业务事实变化时，避免直接覆盖旧内容。这次真实回放发现：原版本把后续报送节点误写成了评审日期。如果直接修改，后来就无法说明旧版写了什么、依据是什么、谁决定纠正。

### 页面动作

停留在“项目总览”，指出当前 Project、Cycle 和交付成果。

### 要证明的事实

- 本次纠错属于明确项目和周期；
- 错误发生在正式版本中，需要受控变更；
- 系统不能静默覆盖历史。

## 0:30—1:05｜查看纠错依据

### 页面动作

进入“资料库”，打开 Source #10，展示两个字段级节点：

1. 县级成果资料报送：2026-09-08 09:00—12:00；
2. 市级成果资料报送：2026-09-14 14:00—17:00；
3. 事实边界：9月14日不是评审日期。

### 讲解

> 这里保存的不是一段无法核对的总结，而是从已授权原通知附件表格中整理出的去标识化字段依据。县级和市级是两个不同业务节点，不能因为日期相邻就把市级报送写成县级成果的评审。

### 要证明的事实

- 纠错结论有来源和表格定位；
- 衍生资料明确标注事实边界；
- 原通知中的个人信息和详细地址没有进入演示材料。

## 1:05—1:55｜查看人工变更决定

### 页面动作

进入“交付清单”，找到已处理的变更请求 #1，打开完整变更报告，依次展示：

1. 修改前：县级成果报送后“参加9月14日评审”；
2. 修改后：只保留9月8日 09:00—12:00的县级成果资料报送；
3. 影响类型：范围变化、验收变化；
4. 三条待验证验收项；
5. 提出人、决定人、决定原因和 Source #10。

### 讲解

> 系统没有根据新证据自动修改正式版本。负责人先提出变更，核对修改前后字段、影响范围和验收清单，再决定是否接受。三条验收项仍然是待验证，因为有要求依据不等于交付已经通过。

### 要证明的事实

- 正式变化经过人工决定；
- 变更原因、字段差异和影响分析可追溯；
- 系统没有把“有依据”误写成“已验收”。

## 1:55—2:35｜查看新旧 Revision

### 页面动作

展开该交付成果的版本历史：

1. 打开第1版，展示原来的错误范围；
2. 打开当前第2版，展示修正后的交付范围和新增验收标准；
3. 指出第2版状态为“已确认”，第1版仍可查看；
4. 返回版本差异，说明当前指针只指向第2版，没有删除第1版。

### 讲解

> 接受变更后，Finto 创建第2版草稿；验收负责人再次确认后，第2版才成为当前确认版本。第1版没有被覆盖，仍然保留当时的内容和状态，所以能够回答“为什么改、从什么改成什么”。

### 要证明的事实

- 第1版 Revision #5 完整保留；
- 第2版 Revision #6 是当前确认版本；
- 变更请求、接受事件和版本差异形成闭环。

## 2:35—3:00｜结果、边界与下一步

### 讲解

> 这次回放纠正了1处业务事实，从提出变更到确认第2版实际用了26分06秒。它证明 Finto 在单机单用户场景中能够完成有依据的版本纠错和追溯，但因为没有记录人工基线耗时，也没有验证全部12条要求，所以不能声称效率提升、完整覆盖、多人协作或生产落地。下一步不是继续扩功能，而是持续用真实但去标识化的变更场景检验这条链是否稳定有用。

## 演示后的证据清单

| 演示结论 | 可核对证据 |
|---|---|
| 纠错依据可定位 | Source #10 的两个附件节点及事实边界 |
| 人工决定发生在正式变化之前 | 变更请求 #1 的 proposed、accepted 事件 |
| 修改内容清楚 | 交付范围和验收标准的前后差异 |
| 没有提前宣称验收通过 | 3 条验收项均为待验证 |
| 旧版本没有被覆盖 | 第1版 Revision #5 仍可打开 |
| 新版本经过再次确认 | 第2版 Revision #6 状态为 confirmed |
| 实际路径耗时有记录 | 10:05:36 提出变更，10:31:42 确认第2版 |

## 演示失败时的降级路径

- 页面无法打开：使用变更报告和版本详情的本地截图，但不展示私人路径或原始资料；
- Source #10 未显示：停止演示证据结论，不凭记忆复述日期；
- 版本历史加载失败：记录 `request_id`，按故障定位 SOP 查日志，不把故障解释成数据已丢失；
- 当前数据被其他演示修改：从备份恢复前先核对数据库和备份时间，不直接覆盖现有数据；
- Windows 安装包出现 SmartScreen：说明当前安装包尚未完成代码签名，不把它解释为业务逻辑故障。

## 一句话收尾

> Finto 的价值不是替负责人自动改答案，而是让每次业务纠错都有依据、有决定、有新版本，也保留旧版本。
