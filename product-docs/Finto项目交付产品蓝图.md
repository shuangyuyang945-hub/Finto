# Finto：项目交付产品蓝图

本版依据用户确认：产品转型为项目交付工具，并纳入前面关于周期、版本、权限、AI候选和人工责任的设计。本文是目标设计，不代表所有能力已经实现。

## 1. 用户为什么打开它

要求分散在资料和反馈中，验收标准会变化。项目负责人需要及时确定交付成果、期限、执行责任和验收依据，并把变化交给执行者。

产品承诺：把授权资料中的要求转成可审查的交付建议，由人决定正式内容，并保留历次依据和责任记录。

第一版使用本机单人工作环境；界面中的负责人字段是责任记录，现有姓名匹配不等于经过登录认证的身份权限。多人部署另行设计认证。

## 2. 完整工作路线

建立项目与当前周期 → 关联项目资料 → 选择本次授权来源 → 创建并运行任务 → 校验候选与来源 → 人工审查 → 创建正式草稿 → 确认、执行、提交和验收 → 查询版本历史。

后续要求变化时：定位受影响的现有交付物 → 比较旧版本和新依据 → 负责人决定新版本 → 保留旧版本 → 明确切换当前版本。此变化路径尚未实现，不能用“再创建一个交付物”代替。

## 3. 信息架构与首页

全局入口为项目列表和设置；进入一个项目后显示项目名称、状态、当前周期和以下导航。

| 页面 | 首要问题 | 主要操作 |
| --- | --- | --- |
| 项目总览 | 今天需要我处理什么？ | 进入待审建议、待确认草稿、临近截止的交付物 |
| 交付清单 | 要交什么，谁负责，何时交？ | 查看交付物、按责任和状态筛选 |
| 交付物详情 | 当前哪一版，依据是什么？ | 查看验收标准、状态流转、历史版本与审计 |
| 待审建议 | AI建议是否可信，如何采用？ | 核对证据与未知项，接受、修改或拒绝 |
| 项目资料 | 本项目依据来自哪里？ | 关联资料，设置AI可用性，选择任务授权 |

首页布局：顶部项目和周期；其下三项行动入口（待审建议、待确认草稿、临近截止）；主体为本轮交付清单；右侧为要求变化和待澄清事项。无数据时提供“关联资料”的真实空状态，不生成假统计。

临近截止暂定未来7天内且尚未验收；逾期为早于今天且尚未验收；日期未确认的项目单独提示，不计入确定逾期。以上为第一版设计假设。

## 4. 一次你能亲手完成的操作

示例资料：阶段成果为数据库和说明文档，交付日期为2026-09-15，验收要求为两者一致。

1. 在示例项目当前周期进入待审建议。
2. 查看AI拆出的“数据库”和“说明文档”，对照每个字段的来源、定位、摘录及未知项。
3. 选择合并，填写“数据库和说明文档”、范围、期限、执行和验收负责人、修改原因。
4. 提交前查看明确预览：2个原候选 → 1个交付物草稿；原始候选保留。
5. 提交后进入新交付物详情，看到草稿状态、审查人、修改原因和证据来源。
6. 通过独立的确认操作进入执行流程；采用AI建议不等于验收通过。

日期仅为示例资料内容，原型不会把示例写入数据库。

## 5. 核心设计如何落地

| 业务要求 | 产品中的落点 |
| --- | --- |
| 明确项目范围 | Project与当前Cycle限定一次交付所属范围 |
| 保留历史 | Deliverable指向当前Revision，旧Revision不可覆盖 |
| 约束AI权限 | AgentJob冻结动作、指令、允许来源和禁止范围 |
| 证明候选依据 | used sources、字段级证据、locator和excerpt共同追溯 |
| 诚实处理缺失 | 资料未说明的内容进入待确认信息，不由系统猜测 |
| 保留人工责任 | 候选必须由负责人接受、修改或拒绝后才能形成草稿 |
| 保护正式数据 | 状态冲突、越权和来源失效时拒绝写入正式业务表 |
| 支持审计 | 原始候选、人审决定、新Revision和失败原因分别留存 |

| 能力 | 当前实际情况 | 改版所需工作 |

## 7. 关键规则

- Project非active时禁止正式业务写入；前端提示不能替代后端约束。
- 请求格式错误400；越权或来源不可用403；对象不存在404；状态冲突409。按具体原因返回，不能统称权限错误。
- used、字段证据、unknowns涉及的来源均需检查；人工修改结果同样不能伪造或扩大来源授权。
- 系统拒绝候选与人工拒绝建议分开记录，保存原因和允许的审计；失败不改变正式交付内容。
- 人工修改保留原始AI输出和人审快照；任务采用状态accepted，人审动作modified；生成的Revision仍是draft。
- 历史内容不覆盖；新版本的创建、当前版本指针切换和审计必须一致完成。

## 8. 旧功能处理与实施顺序

历史资料库功能退出交付主导航；已有本地文件和数据保留。旧资料不会自动变成已授权项目资料，必须明确关联和授权。

第一步：审阅配套HTML布局原型，确认页面是否能让用户知道下一步做什么。

第二步：实现项目总览与交付清单的真实读取、项目选择、空状态，替换旧首页导航。

第三步：完成待审建议的证据/未知项、修改预览、来源再校验和提交后详情；不硬编码示例范围及原因。

第四步：闭合交付状态、验收标准和历史版本，并完成项目/周期约束验证。

每一步都以一条用户可操作场景和自动化回归作为验收依据，不以页面展示代替后端业务约束。
