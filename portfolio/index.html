01

从真实交付问题出发

问题不在“有没有文档”，而在变化发生后还能否说清楚。

散

验收要求分散

任务书、通知、报告和反馈分别保存，字段依据难以定位，整理时容易遗漏或误读。

改

修改直接覆盖

业务事实或交付口径变化后，旧版本被覆盖，难以回答“为什么改、从什么改成什么”。

责

系统越过负责人

AI 可以提出候选，但不能替业务负责人确认事实、接受变更或宣布验收通过。

02

Human in the loop

把 AI 放在可控的位置，把决定留给负责人。

01

授权资料

任务执行前冻结可用来源、动作和禁止范围，避免模型自行扩权。

02

提取候选

零 Token 规则解析或大模型 API 生成候选字段，不直接写入正式交付物。

03

核对依据

候选携带字段级来源、定位与待确认信息，支持人工逐项复核。

04

人工决定

负责人原样接受、修改后接受或拒绝，所有决定进入审计记录。

05

创建版本

只有接受后才创建正式 Revision；新版本生效，旧版本仍可追溯。

能力与边界

展示已经完成的，也清楚说明尚未验证的。

✓ 已实现

  • 项目、周期、交付物与 Revision 版本历史
  • 任务级来源授权、字段证据与人工审查
  • 本地规则解析与 OpenAI-compatible AI 模式
  • PDF、DOCX、XLSX、CSV、TXT、Markdown 资料处理
  • 变更影响分析、审计记录与 Windows 本地运行

— 当前边界

  • 个人实践项目，业务验证来自历史案例回放与本人使用
  • 单机单用户，没有账号、多人并发权限与远程部署
  • 负责人是业务流程字段，尚未实现登录身份鉴权
  • 扫描图片型 PDF 尚不支持 OCR
  • 不宣称企业级平台、生产落地或外部市场验证
